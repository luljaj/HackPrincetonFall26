# Learning pipeline contracts

Import public runtime schemas and inferred types from `lib/contracts` (or a specific module). This barrel is browser-safe: it imports only Zod and other public contracts, never provider clients, Node APIs, scene instances, storage, or secrets. Scene configuration and question-context schemas describe private authoring data; their values and answer guides stay on the server. Public questions contain only `questionId` and `text`.

Every object rejects unknown fields, including nested objects. Nullable fields are required explicitly. Session and interaction IDs are UUIDs; authored scene/objective/question IDs are nonempty strings up to 128 characters. Generated variant IDs are UUIDs, validated against session history. Question text is limited to 300 characters, objective to 500, answer guide to 1,000, and scene facts to 20 items of 300 characters. Other application defaults bound speech to 2,000 characters, transcripts to 10,000, and parent summaries to 200; revise these deliberately with the authored demo content.

`response.text` is the complete speech, including a follow-up question. Speak it once. `nextQuestion.text` is metadata and must not be appended as more speech. `nextQuestion` is the active question after processing: a new variant, the same question during clarification, or null when finished. Episode progression remains with the cartoon controller. Saved responses mean processed and selected; they do not establish playback or that assistance was heard.

The original wrong answer stays in history and exposes one pending variant immediately. An assessed variant finishes regardless of correctness. Clarifications retain the current question ID and do not consume another variant. Identify original versus variant by question ID/history rather than turn count. Assistance before an answer excludes help in its newly generated response and stays true once selected help exists for this objective.

Create a session with the prepared `sceneId`. Submit multipart audio plus `interactionId`, `questionId`, and `expectedTurnNumber`; convert the multipart turn number to a nonnegative integer before schema validation. The production metadata contract accepts no client transcript. Append a real `File` with its actual container and let the browser set multipart Content-Type.

A client retains the original recording and reuses its interaction UUID only to retry that exact submission. A newly recorded answer always gets a new interaction UUID. Duplicates are scoped to session plus interaction and return the saved public response before stale-version checking. No request comparison or audio hashing is required.

`SessionProgress` includes the current public question before its answer exists, ordered evidence, and canonical counts/latest status (including `not_assessed`). Parent summary is the latest non-null stored summary; empty-transcript clarifications preserve earlier summaries. Parent reads exclude diagnostics, answer guides and raw drafts. `SessionUpdatedEvent` contains only committed IDs/version and is emitted after persistence; consumers refetch progress.

Private schemas live in `server/pipeline/luna-contract.ts` and `server/storage/contract.ts`. These are pure validation modules so Node tests can import them. Backend entry points/provider clients use `server-only`; the authored-scene registry is guarded. `PipelineStore` specifies atomic commit/version/replay semantics without choosing an adapter. Session snapshot validation checks ordered scope, question transitions, sticky assistance, latest summary, and exact replay agreement. No raw audio belongs in these records. `ProgressReader` lives with the shared progress contract.

Synthetic sample requests, responses, pending progress and terminal progress are in `fixtures/index.ts`; the synthetic scene is in `server/scenes/example.scene.ts`. These are development examples, not the final scene owner's content. Run `npm run test -w web` for boundary checks. No provider calls are needed.
